# ステータスと商品名の流れ（status-and-title-flow）

- 作成日: 2026-11-19
- ブランチ: `fix/title-display-and-prefix-stack`（この文書は同ブランチの修正を反映した内容。修正前の挙動は「修正前」と明記）
- 対象コード: `gas/Main.js` / `gas/TitleLogic.js` / `gas/WebApi.js` / `gas/SheetRepo.js` / `gas/Constants.js` / `js/app.js`

## 1. 商品名を持っている場所

| 場所 | 列・項目 | 意味 | 画面での表示 |
|---|---|---|---|
| 楽天RMS | 商品名 | 実物。ツールが書き換える対象 | — |
| `T_{sid}`（対象商品） | B列 `baseTitle` | 直近の実行でRMSから取得した商品名から、イベントprefixを外したもの | 「現在の商品名」が空のときだけ代わりに表示 |
| `T_{sid}` | C列 `currentTitle` | **「対象商品」タブの「現在の商品名」**。RMSの実際の商品名を保存する（修正後） | 対象商品タブ |
| `T_{sid}` | D列 `lastUpdated` | その商品を最後に**処理した**日時（商品名を変えた日時ではない。スキップ・手動変更でも更新される） | 最終更新 |
| `T_{sid}` | E列 `status` | 直近の実行結果（下記 3 章） | ステータス |
| `B_{sid}`（バックアップ） | `originalTitle` | その商品を**初めて処理した時点**の商品名（prefixを外したもの）。手動変更検知の比較基準。以後は自動更新されない | 表示なし |
| `L_{sid}`（ログ） | `oldTitle` / `newTitle` | 実行時点のRMSの商品名／書き換え後（予定）の商品名 | ログタブ |
| `R_{sid}`（予約） | `originalTitle` / `newTitle` | 即時適用の直前の商品名／適用した商品名。復元時は `originalTitle` に戻す | 予約実行タブ |

イベントは全店舗共通の `EVENTS` シートのみ（店舗別のイベントシートは現在のコードには無い）。

## 2. 「現在の商品名」（`currentTitle`）が書き換わるタイミング

| タイミング | 処理 | 書き込む値 |
|---|---|---|
| 商品追加 | `WebApi.js` `handleBulkAddTargetItems_` | 追加時にRMSから取得した商品名（取得失敗時は空） |
| 定期実行・手動実行 | `Main.js` `processItems` | 下表のとおり |
| 更新ボタン（対象商品タブ） | `WebApi.js` `handleSyncTargetTitles_`（新規） | RMSから取得した実際の商品名。この列だけを書き換え、ステータス・最終更新・バックアップは変えない |
| タブ切替・画面読み込み | `handleGetTargetItems_` | 書き換えなし（シートの値を表示するだけ） |
| 即時適用・予約復元・予約キャンセル | `handleApplyNow_` / `checkAndRestoreScheduled` / `handleCancelReservation_` | **書き換えない**（RMSとログ・予約シートのみ更新）。次回の定期実行か更新ボタンで反映される |

定期実行・手動実行で書き込む値:

| 実行結果 | 修正後 | 修正前 |
|---|---|---|
| RMSを更新した（SUCCESS） | 新しい商品名 | 同じ |
| 変更なし（SKIPPED） | RMSの商品名（＝生成した商品名と同じ） | 同じ |
| 手動変更（MANUAL_CHANGE） | **RMSの実際の商品名** | **書き換えない（前回の値が残り続ける）** ← 表示が食い違う原因 |
| DryRun（DRY_RUN） | **RMSの実際の商品名**（更新予定の商品名はログで確認） | 更新予定の商品名（RMSは未変更なのに変更後の名前を表示） |
| RMS更新に失敗（FAILED） | **RMSの実際の商品名に戻し、ステータスも FAILED** | 更新予定の商品名・SUCCESS のまま残る |
| 商品取得に失敗 | 書き換えなし（ログにのみ FAILED を記録） | 同じ |

## 3. ステータス一覧

`T_{sid}` の E列に入る値。画面のバッジは `js/app.js` `loadTargetItems`。

| 値 | 画面表示 | 判定条件（`Main.js` `processSingleItem` / `processItems`） | 次回実行時の扱い |
|---|---|---|---|
| `新規追加` | 新規 | 商品追加直後。まだ一度も処理されていない | 通常どおり処理。初回処理時にバックアップを作成 |
| `SUCCESS` | 成功 | 生成した商品名がRMSと異なり、RMSを更新した | 通常どおり処理 |
| `SKIPPED` | スキップ | 生成した商品名がRMSの商品名と同じ（変更不要）。**正常な状態**（イベント中の2回目以降・イベントが無い平常時はこれになる） | 通常どおり処理 |
| `MANUAL_CHANGE` | 手動変更 | prefixを外したRMSの商品名と、バックアップの商品名の類似度が80%未満（`TitleLogic.js` `detectManualChange`） | **毎回RMSから取り直して再判定する。** 類似度が80%以上に戻れば自動的に通常処理へ復帰。戻らない限りスキップされ続け、prefixの付与も除去も行われない |
| `DRY_RUN` | DRY_RUN（灰色） | 稼働状態がテスト中、または手動実行の「DryRun実行」で、変更が必要と判定された | 通常どおり処理 |
| `FAILED` | 失敗 | RMSの更新APIがエラー（修正後のみシートに反映） | 通常どおり処理（再試行される） |
| `API取得失敗` / `エラー: …` | そのまま表示（灰色） | 商品追加時にRMSから商品名を取得できなかった | 通常どおり処理 |

### 手動変更（MANUAL_CHANGE）について

- 類似度の計算（`calculateSimilarity`）: 一方が他方を含む場合は「短い方の文字数 ÷ 長い方の文字数」、そうでなければ「短い方の文字のうち長い方に含まれる文字数 ÷ 長い方の文字数」。
- バックアップは初回処理時に1度だけ作られ、その後は更新されない。**手動変更の検知時にバックアップをRMSの値で更新しないのは仕様**（更新すると比較基準が変わり、検知そのものが無意味になるため）。
- 解除する方法:
  1. RMSの商品名をバックアップに近い内容へ戻す（類似度80%以上）
  2. バックアップをリセットする（API `resetBackups`。**店舗の全商品が対象**で、次回実行時の商品名が新しい基準になる。画面にボタンは無い）
  3. `B_{sid}` シートの該当行を手で削除する（その商品だけ基準を取り直す）
- 対象商品から削除して追加し直しても、`B_{sid}` の行は残るため解除されない。

## 4. prefix の付与と除去

### 定期実行（`run` → `runForStore` → `processItems`）

1. `EVENTS` シートから、いま期間内で有効なイベントを取得（複数可、優先度順）。
2. 既知のprefix文言を登録する（`setKnownEventPrefixes_`、修正で追加）。
   - `EVENTS` シートの全行（無効・期間外を含む）の long / mid / short
   - 過去の即時適用で使われたprefix（復元済み・キャンセル済みのもの）
   - `Constants.js` `LEGACY_EVENT_PREFIXES`（過去に使われた文言。現在は「【予告】お買い物マラソン」）
3. 商品ごとにRMSから商品名を取得し、先頭のprefixをすべて外す（`stripEventPrefixes`）。
   - 固定パターン（`EVENT_PREFIX_PATTERNS`: 5の日・0の日・マラソン・いちばの日・ワンダフルデー・当店倍率）
   - 2 で登録した文言（文字列の前方一致。長い文言を優先）
4. 手動変更を判定（3 章）。
5. 外した商品名の先頭に、適用中イベントのprefixを付ける（127文字に収まらない場合は prefix を短くする → 商品名を短縮する）。イベントが無ければprefixなし。
6. RMSの商品名と違えば更新、同じならスキップ。

### 多重付与が起きていた原因（修正前）

- 修正前の `stripEventPrefixes` は固定パターンしか外せなかった。
- `EVENTS` シートには任意の文言を登録できる（イベント追加の「カスタム」、イベント編集）。
  「【予告】お買い物マラソン」は固定パターンのどれにも一致しない。
- そのため実行のたびに「外せない → さらに先頭へ付ける」が繰り返され、1回の実行につき1つずつ増えた。
- 増え続けると、バックアップとの類似度が80%を下回った時点で手動変更と判定されて止まる。
  同じ理由で、イベント終了後もprefixは外れずに残った。

### 即時適用（`handleApplyNow_`）・予約復元（`checkAndRestoreScheduled`）

- 即時適用: RMSの商品名から既知のprefixを外し、指定の文言を1つ付ける（`buildApplyNowTitle_`）。
  修正後は同じ文言・過去の即時適用の文言・`EVENTS` の文言も外してから付けるため、重ね付けにならない。
- 適用中（APPLIED）の即時適用prefixは、定期実行では外さない（復元予約の時刻まで残すため）。
- 予約復元・キャンセル: 即時適用の直前の商品名（`R_{sid}` の `originalTitle`）をそのまま書き戻す。prefixの付け足しは行わない。

## 5. 既知の制限（未対応）

- **過去に使った文言が `EVENTS` にも `LEGACY_EVENT_PREFIXES` にも無い場合は外せない。**
  イベント行を編集・削除する前にRMSへ付与済みの文言が該当する。見つけたら `LEGACY_EVENT_PREFIXES` に追加する。
- **商品名が長く短縮された場合、イベント終了後に元の長さへは戻らない。**
  prefixを外した結果（短縮後の商品名）がそのまま残る。バックアップからの復元は行っていない。
- **`EVENTS` に登録した文言と同じ文字列で始まる商品名は、その部分がprefixとして外される。**
  （例: prefixに「【送料無料】」を登録すると、もともと「【送料無料】」で始まる商品名からも外れる）
- 即時適用・予約復元の直後は「現在の商品名」が古い（次回の定期実行か更新ボタンで反映）。
- 更新ボタンの同期は商品1件ごとにRMSへ問い合わせるため、件数に比例して時間がかかる（1件あたり約1秒）。
  4分で打ち切り、残りは未処理件数として表示する。定期実行中は同期できない。
